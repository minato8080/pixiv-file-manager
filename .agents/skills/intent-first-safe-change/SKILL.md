# Intent-First Safe Change

変更タスクを「意図の見立て → 必要な確認 → 最小変更 → 実証 → 簡潔な報告」で進める軽量な作業規律。目的は質問や設計儀式を増やすことではなく、結果を変える思い込みと未検証の完了宣言を防ぐこと。

## 1. 意図を短く見立てる

依頼文、会話、既存の文脈から、着手前に次の4点を内部で一行ずつ整理する。

- **Outcome**: 何ができれば依頼達成か
- **Target**: どのファイル、機能、データ、環境が対象か
- **Constraints**: 変更してはいけないもの、既存の規約、権限境界
- **Proof**: 何を確認できれば達成と言えるか

明示された依頼と上位のプロジェクト規約を、推測や好みより優先する。明確な小さな変更を、重い設計レビューや承認儀式へ膨らませない。

## 2. 既存の文脈を先に確認する

編集や実装の前に、対象に関係する範囲だけを確認する。

- 既存コード、ファイル構成、命名・実装パターン
- 要件、設計、設定、Issueなどの正本
- 関連テスト、lint/type/buildの実行方法
- 既存の差分、作業状態、未コミット変更

既存の流れがあるならそれに合わせる。関係のないファイルまで探索して作業を広げない。読み取りだけの質問には、変更タスクの手順を無理に適用しない。

## 3. 質問の閾値を決める

確認できる文脈を見た後、次の答えが変わる曖昧さだけ質問する。

- 対象、データ、環境、互換性が変わる
- 挙動、公開インターフェース、受入条件が変わる
- 削除・上書き・外部送信などの副作用や権限が変わる
- 正本同士が矛盾し、どちらを採用するかで結果が変わる

それ以外で依頼を安全に実行できるなら、質問せずに進める。安全な既定値が結果を変えない場合はそれを採用する。質問する場合も、最小の問いを一度に一つだけ聞く。作業中に結果を変える曖昧さが判明したら、その地点で止めて確認し、推測で分岐しない。

## 4. スコープを固定して最小変更にする

着手前に、次の形で境界を一文にする。

> `<対象>` に `<必要な変更>` だけを行い、`<成功条件>` を満たす。

その境界に必要な最小のファイル・コード・設定だけを変更する。勝手なリファクタリング、命名変更、整形、依存追加、掃除、仕様拡張、隣接バグの修正は行わない。発見した改善案は、現在の結果に必須でない限り記録して後回しにする。正しさ・安全性・互換性を守るために不可欠な追加だけは、理由とともにスコープへ明示する。

ユーザーが依頼していない外部作用（push、merge、送信、公開、削除など）の許可を推測しない。上位規約に従う必要がある場合を除き、必要な許可だけ質問する。

## 5. 完了前に実証する

完了、成功、修正済み、問題なしと報告する前に、次を行う。

1. Outcomeと成功条件を読み直し、実際の変更が一致するか確認する。
2. 変更箇所に対応する新鮮で十分な検証を実行する。通常は対象を絞ったテストを先に行い、必要に応じてsyntax、lint、型、build、統合確認を追加する。
3. コマンドの終了コードと出力を読み、失敗数・警告・未検証部分を確認する。
4. 元の症状または要求された挙動を直接確認する。
5. diffと作業状態を確認し、スコープ外の変更や既存差分を混ぜていないことを確かめる。

検証を実行できない場合は、何がなぜ実行できないかを残課題に書く。「たぶん通る」「見た目は正しい」「別の検証が通った」だけで成功を主張しない。検証失敗時は修正して再実証するか、未完了として報告する。

## 6. 報告を短くする

上位ルールに別の必須形式がなければ、次の4項目で報告する。残課題がなければ「なし」と書く。

**何をした**
- 変更した対象と結果。

**なぜ**
- 依頼のどの目的を満たすためか。

**検証結果**
- 実行したコマンドまたは確認方法と、実際の結果。

**残課題**
- 未完了、未検証、保留したスコープ外事項。なければ「なし」。

検証前に完了を示す言葉を使わない。報告は実際に行った変更と証拠だけに基づけ、予定や推測を実績として書かない。
